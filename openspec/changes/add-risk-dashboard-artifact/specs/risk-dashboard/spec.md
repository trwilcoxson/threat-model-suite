## ADDED Requirements

### Requirement: The dashboard is a self-contained offline artifact
The suite SHALL generate a product-risk dashboard as a single self-contained `dashboard.html` file with
inline CSS and JavaScript and no external CDN, font, or asset references, so it renders offline like the
suite's other artifacts. The dashboard SHALL NOT load any network resource.

#### Scenario: Dashboard renders with no network
- **WHEN** `dashboard.html` is generated for a run and opened without network access
- **THEN** it renders fully, and it references no `http(s)://` or protocol-relative resource

#### Scenario: Deterministic output
- **WHEN** the dashboard is generated twice from the same manifests
- **THEN** the two `dashboard.html` files are byte-identical (no embedded timestamps or randomness)

### Requirement: The dashboard is generated by a deterministic transform over emitted facts
The dashboard SHALL be produced by a deterministic generator that reshapes `recon.json`,
`findings.json`, and `coverage.json` (and the ATT&CK navigator layer when present) into the view. The
generator SHALL NOT compute new security judgments; every security fact shown SHALL come from the
manifests, preserving the determinism boundary.

#### Scenario: Every headline number is grounded
- **WHEN** the grounding check runs over a generated dashboard and its manifests
- **THEN** each headline count (severity bands, findings total, kill-chain count, coverage percentage)
  equals a recount of the corresponding manifest field, and no finding identifier appears in a
  structural slot unless it exists in `findings.json`

#### Scenario: Absent facts are not invented
- **WHEN** a run's `findings.json` contains no `controls`, `cvss_vector`, or `atlas`, or its
  `recon.json` contains no `dataflows`
- **THEN** the dashboard renders those sections as empty states and shows no fabricated value for them

### Requirement: The dashboard is templated and degrades gracefully
The dashboard SHALL have a fixed section inventory that is the same for every run. When a section's
source data is absent or empty, that section SHALL render a graceful empty state and the overall layout
SHALL remain intact.

#### Scenario: Sparse run keeps the layout
- **WHEN** the dashboard is generated from a run with few findings and no kill chains or external
  dependencies
- **THEN** every section still renders in its fixed position, empty sections show an empty/"no evidence"
  state, and no section is missing or broken

#### Scenario: Empty run does not crash
- **WHEN** the generator runs against a run with empty or missing manifests
- **THEN** it produces a valid dashboard with all sections in their empty state rather than erroring

### Requirement: The dashboard embeds the run's actual structural diagram as its interactive explorer
The dashboard SHALL embed the run's own rendered structural diagram — the same recon-derived structural
graph the flow produces elsewhere (the `recon_to_d2.py`/`structural-diagram` render of this run's
`recon.json`, with the same nodes, layout, and edges as `structural-diagram.mmd`/`.svg`) — rather than a
bespoke, independently-laid-out "system map". The embedded diagram's node ids SHALL be the run's recon
element ids (`C1`/`D1`/`E1`/`X1`…) so they link natively to the findings that reference them, and its
edges SHALL be the run's real dataflows (`recon.dataflows[]`), NOT edges synthesized from finding
co-reference. Over that embedded diagram the dashboard SHALL layer pan/zoom and a click→cross-filter
shared selection connecting findings, components, data stores, entry points, trust boundaries, external
dependencies, kill chains, and frameworks. The linked model SHALL be precomputed from real identifiers
in the manifests and SHALL NOT contain any relationship not present in the emitted facts. Selecting any
data point SHALL cross-highlight and cross-filter every related point across the diagram and all panels
through one shared selection.

#### Scenario: The embedded diagram is the run's real diagram, not a substitute
- **WHEN** the dashboard is generated for a run
- **THEN** its embedded diagram is this run's rendered structural diagram artifact (same nodes, layout,
  and dataflow edges as the diagram the flow emits elsewhere), its node ids are the run's recon element
  ids, and no independently laid-out or differently-sourced diagram is substituted

#### Scenario: Edges are the run's real dataflows, not finding co-reference
- **WHEN** the embedded diagram is rendered
- **THEN** every edge corresponds to a declared `recon.dataflows[]` item between two declared recon
  elements, no edge is synthesized from findings co-referencing each other, and when `recon.dataflows[]`
  is absent no typed flow edge is fabricated

#### Scenario: Pivot is grounded in the manifests
- **WHEN** a user selects an entity, finding, framework, kill chain, or severity band
- **THEN** exactly the findings and entities that reference it in the manifests are highlighted, and no
  unrelated relationship is shown

#### Scenario: Interactivity degrades gracefully
- **WHEN** the run has no recon entities or no findings
- **THEN** the embedded diagram renders an empty state and the dashboard remains usable without errors

### Requirement: The dashboard reconciles to the run's manifests by a reference-free cross-output check
Every number and visual the dashboard shows SHALL equal the run's canonical manifests, so the dashboard
is one more view of the single source of truth rather than an independent artifact. A reference-free
consistency check (no answer key) SHALL verify that the dashboard-derived values reconcile to the
manifests: the dashboard severity counts SHALL equal `findings.summary_counts`, the coverage percentage
SHALL equal the value derived from `coverage.json`, the finding ids and text SHALL match `findings.json`,
the embedded diagram's nodes SHALL equal the run's recon elements, and the kill chains SHALL match
`findings.kill_chains`. The check SHALL confirm the embedded diagram is the run's real structural diagram
artifact and not a generated substitute.

#### Scenario: Dashboard numbers reconcile to the manifests
- **WHEN** the cross-output consistency check runs over a generated dashboard and its run manifests
- **THEN** the dashboard's severity counts equal `findings.summary_counts`, its coverage percentage
  equals the value derived from `coverage.json`, its embedded diagram's nodes equal the recon elements,
  and its kill chains equal `findings.kill_chains`

#### Scenario: A drifted number or substituted diagram is caught
- **WHEN** the dashboard shows a count, coverage value, finding id, diagram node set, or kill chain that
  does not reconcile to the corresponding manifest, or embeds a diagram that is not the run's real
  structural diagram artifact
- **THEN** the cross-output consistency check reports a defect

### Requirement: The dashboard is an additive, opt-in output
The dashboard SHALL be an additional output that does not replace or alter `report.html`,
`report.docx`, `report.pdf`, `executive-summary.pptx`, or the analytical visuals. It SHALL be produced
only when selected in the run plan's outputs.

#### Scenario: Existing outputs unchanged
- **WHEN** a run generates the dashboard
- **THEN** all previously supported outputs are still produced unchanged when they are selected

#### Scenario: Dashboard is opt-in
- **WHEN** the run plan's outputs do not include the dashboard
- **THEN** no `dashboard.html` is produced
